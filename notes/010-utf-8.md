# 010: utf-8, storing those numbers in 1 to 4 bytes
builds on: [004 bytes, 8 bits and 256 possible values](./004-bytes.md), [006 one byte, two hex digits](./006-one-byte-two-hex-digits.md), [007 text is numbers, one character and one number](./007-text-is-numbers.md), [008 ascii runs out, 128 spots isnt enough for the world](./008-ascii-runs-out.md), [009 unicode, one number for every character](./009-unicode.md)
section: data at the atom level, part 10, ~2 min read

why is é one character on your screen but two bytes in a file?

in [009](./009-unicode.md) Unicode, one table numbering every character, gave each [character](./007-text-is-numbers.md) a code point, and ઢ got 2722. a [byte](./004-bytes.md) holds only 0 to 255, so thats too big. UTF-8 is the fix: it stores each code point in 1 to 4 bytes, fewer bytes for smaller numbers.

| code point | bytes used | example |
|---|---|---|
| 0 to 127 | 1 | d |
| 128 to 2047 | 2 | é |
| 2048 to 65535 | 3 | ગ, another gujarati letter |
| 65536 to 1114111 | 4 | 🙂 |

one caveat, 55296 to 57343 are reserved and never hold a character.

```python
for ch in ["d", "é", "ગ", "🙂"]:
    b = ch.encode("utf-8")
    print(ch, ord(ch), len(b), b.hex(" "))
```

```output
d 100 1 64
é 233 2 c3 a9
ગ 2711 3 e0 aa 97
🙂 128578 4 f0 9f 99 82
```

the last column is the bytes in [hex](./006-one-byte-two-hex-digits.md), two digits per byte. the shop, the imaginary snack store these notes run on, has english names like dhokla and jalebi, so they sit in the first row, one byte each.

and that first row is the clever part. 0 to 127 is exactly the old [ASCII](./008-ascii-runs-out.md) table, and the byte is the same number it always was, so a file of plain english letters and digits is already UTF-8 without changing a byte. the bytes for é, ગ and 🙂 are all 128 or higher, so none of them can ever be mistaken for an ASCII letter hiding inside a bigger character.

what would you pick? i first guessed just give every character 4 bytes and be done. that works, but every english file would get 4 times bigger.

so a character count and a byte count stop agreeing, and the one character one byte idea from [007](./007-text-is-numbers.md) only holds for ASCII. "é" is 1 character and 2 bytes, and anything that measures bytes, like a file size, sees the second one.

### check yourself

1. the query below adds an é to the end of the shop product jalebi. predict both byte counts. strlen counts bytes in DuckDB.
```sql
SELECT name, strlen(name) AS bytes, strlen(name || 'é') AS with_accent FROM products WHERE name = 'jalebi';
```
<details><summary>answer</summary>

```result
name | bytes | with_accent
jalebi | 6 | 8
```
the 6 letters are ascii, 1 byte each, and é costs 2. the tempting answer is 7, from counting one new character as one new byte.

</details>

2. a text column holds at most 10 bytes. how many é fit, and how many plain d?
<details><summary>answer</summary>

5 é, since each is 2 bytes, and 10 d, since each is 1. the tempting answer is 10 of each, from counting characters instead of bytes.

</details>
